## Why no Maestro flow was edited

`.maestro/database.yaml` (`npm run test:smoke:database`) already asserts the
fresh-install migration path and the reopen path against an already-migrated
database on both platforms. Migration 3 rides those assertions unchanged: this
issue adds no screen, no control, and no selector, so a new leg would have
nothing new to select. Per `smoke-verification.md` §4, a flow written blind that
cannot match anything is worse than no flow, so nothing was added.

This machine additionally has no JDK, no Android SDK, and no iOS simulator
runtime (`smoke-verification.md` §1), so **no `test:smoke:*` script can run at
all**, regardless of platform. The only device surface is the owner's physical
iPhone via `npx expo start`.

## Still on-device-unverified

**Migrating a real installed version-2 database on a real `expo-sqlite` build.**
The harness proxy is `node:sqlite` **3.50.4**; the device runs the SQLite
`expo-sqlite` **57.0.1** vendors, which is **3.50.3**
(`node_modules/expo-sqlite/vendor/sqlite3/sqlite3.h`). Same release line, one
patch apart — which narrows the portability gap this entry exists to close but
does not close it, because the vendored build's compile-time options and the
native call's error-message wrapping are still unobserved here.
Everything migration 3 uses is long established (`trim(X,Y)`,
`char()` since 3.8.3, named constraints, `foreign_key_check` since 3.7.16), and
the recipe deliberately does not depend on the one genuinely version-sensitive
behaviour in this area — `ALTER TABLE … RENAME TO` rewriting other tables'
`REFERENCES` clauses, which changed in 3.25 — because foreign keys are off for
the rename and the old table is dropped first. So the two engines should behave
identically. **Should** is exactly what this entry exists to close.

One schema-text side effect to know about before comparing schema SQL in a
future migration or test: after step 7's `ALTER TABLE … RENAME TO`, the rebuilt
tables' `sqlite_master.sql` reads `CREATE TABLE "pattern_step" (…)` and
`CREATE TABLE "guide_step" (…)` — the identifier is **quoted**, where every
version-1 table's stored DDL is not. It is harmless and normal, but a byte
comparison of stored DDL across versions will see it.

Provisional acceptance criterion: AC3, "Migration from the previous schema
version with realistic existing data preserves every row, every `origin`, every
position, and both `UNIQUE (…, position)` constraints" — **provisionally met, the
real-device upgrade of an installed version-2 database deferred to #16 by owner
decision <https://github.com/ciaran-slow/MellowMaker/issues/67#issuecomment-5551072681>.**
Row-loss count on a real device: **UNMEASURED.**

### Owner-run script (iPhone via `npx expo start`)

No agent clock is involved; every step is observable by eye.

1. On `main`, `npx expo start`, open the app on the iPhone. Create a pattern with
   three steps. Tick one step off. Open it in the viewer so an active step is
   set. Set the counter to **7**. Then import a guide and paste a chapter list so
   it holds at least two `origin: 'import'` steps with timestamps.
2. Stop Metro. Check out `main` at or after `4980f4e` (#71 is merged, so its
   branch no longer exists). `npx expo start` again. **Do not clear
   the app's data** — the existing SQLite file is the entire point. Reopen the
   app.
3. Confirm, by looking: every pattern step and its order; the ticked step still
   ticked; the active step still where it was; the counter still at **7**; every
   pasted guide step with its timestamp. And that **no** "We couldn't open your
   saved making data" state appears.
4. In the guide editor, try to save a step whose instruction is only spaces. The
   existing field-level message appears and nothing crashes — the schema floor is
   underneath that guard, not in front of it.

**Pass condition:** step 3 shows **zero** lost rows. Any loss is a migration
defect — specifically the foreign-keys-off hazard in architecture §7 rule 9 —
and not a selector miss.
