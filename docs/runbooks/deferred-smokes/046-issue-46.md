### 1. fps cascade — plan §6.8 step 3, threshold (1)

Dev menu (shake) → *Toggle performance monitor*. Navigate back to the stitch list and re-enter *Single crochet* detail **three times**; record the **minimum UI fps** and **minimum JS fps** during each cascade. If the performance monitor is unavailable in that Expo Go build, record a slow-motion screen capture instead and count dropped frames across the cascade — **do not skip the measurement**.

**Threshold:** minimum UI fps **≥ 55 across all three runs**. This is the one input the provisional GO is contingent on. If it fails, the plan's pre-registered fallback applies: re-scope to **one animation per stitch instead of per step** and re-measure.

### 2. Reduce Motion quit-and-reopen — plan §6.8 step 4, AC2's device half

iOS Settings → Accessibility → Motion → **Reduce Motion on**. **Fully quit and reopen Expo Go** — Reanimated reads the preference at start-up, which is why a live toggle does not exercise this — then re-enter *Single crochet*.

**Threshold:** every step shows its **completed drawing immediately**, nothing animates, and the text appears with **no delay**. Turn Reduce Motion back off afterwards. Jest pins this branch at the hook, the component, and the screen; the device run is what proves it on the real Reanimated runtime.

### 3. Airplane-mode render — plan §6.8 step 5

Airplane mode on in Control Centre, then navigate list → detail → back.

**Threshold:** the art **still renders**. Stated honestly: Expo Go serves the JS bundle from the dev server, so a true offline **cold start** is not demonstrable there — that claim rests on `tests/offlineColdStart.test.tsx`, the component's throwing-`fetch` render, and the art being inline TS in the bundle. The real airplane-mode cold start is itself part of what #16 clears.
