## Proxy coverage that ran

Jest `PatternViewerScreen`'s new `opens at the current step (issue #63)` block,
eight cases, each against a `jest.spyOn(FlatList.prototype, 'scrollToIndex')`
that **calls through** to the real `VirtualizedList` (case 4 excepted, and for a
stated reason):

1. **Scrolls to the current step on the first content-size change** — a 24-step
   pattern with the active step at index 19: no `scrollToIndex` from `render`
   alone, then exactly `{ animated: false, index: 19, viewPosition: 0 }` after
   one `contentSizeChange`.
2. **Retries a failed attempt on the next content-size change** — the list
   carries an `onScrollToIndexFailed` function at all (it was `undefined`
   before), and two fires produce two attempts at index 19, so an
   optimistically-settled restore cannot pass.
3. **Gives up after five attempts** — six fires produce five calls, a seventh
   still five. The literals `5`/`6`/`7` are written in the test;
   `MAX_RESTORE_ATTEMPTS` is deliberately not imported.
4. **Settles for the mount as soon as an attempt does not fail** — here the spy
   is a `mockImplementation` no-op, standing in for a landing: it records the
   call and does *not* invoke `onScrollToIndexFailed`, which is what a measured
   cell looks like to this hook. One fire, one call; two further fires, still one
   call, with only two of five attempts spent so the cap cannot be what stopped
   them. Added by the build stage's mutation self-check, not in the plan's list
   of seven — see the PR body.
5. **No attempt when the current step is already the first row** — 24 steps, none
   complete: two fires, zero calls. Index 0 is *not* an unmeasured index, so a
   missing guard would really scroll rather than fail softly.
6. **No attempt when there is no current step at all** — an empty pattern, and a
   24-step pattern with every step complete: zero calls in both. Without the
   guard each trips a `VirtualizedList` invariant (`item length 0 but minimum is
   1`; `requested index -1 but minimum is 0`) and the screen throws.
7. **Never re-scrolls on a completion or a counter tap, but a fresh open restores
   again** — one attempt, then a completion tap and a counter tap that both
   genuinely land (counter value and SQLite completion asserted) with the call
   count still 1, then a remount that restores to the *new* current step.
8. **The failure payload is never turned into an offset** — a `readFileSync`
   source guard over `usePatternPositionRestore.ts` asserting it contains none of
   `averageItemLength`, `highestMeasuredFrameIndex`, `scrollToOffset`, and that
   the handler is parameterless.

Unchanged and green alongside them: the 20 pre-existing `PatternViewerScreen`
cases — including the whole frozen `one scroll surface (issue #56)` block, which
this PR leaves byte-identical (#63 AC4) — the 6 `patternsNavigation` cases, and
the four walk guards `offlineColdStart` / `loggingHygiene` /
`accessibilityContrast` / `textScaling`, which pick the new `src/` file up by
default with no new exemption.

## Still on-device-unverified

**What Jest cannot reach.** Jest has no layout engine, so
`getHighestMeasuredCellIndex()` is `0` and every attempt above index 0 takes
`VirtualizedList`'s failure branch. The suite therefore pins the **intent** — the
right index, at the right moment, exactly the right number of times, and never at
the wrong moments — and can never pin the resulting **pixel offset**. The offset
is guaranteed *by construction* (with no `getItemLayout`, only a measured cell is
ever scrolled to, and a measured offset is content-container-relative and so
already contains the header) rather than by test. Step 3 below is what observes
it.

These acceptance criteria are **provisionally met — the on-device landing
position deferred to #16 by owner decision
[link](https://github.com/ciaran-slow/MellowMaker/issues/63#issuecomment-5551016820)**:

- **AC1** — "Opening a pattern whose active step is far down the list brings that
  step into view without a manual scroll."
- **AC2** — "The mount-time path cannot scroll to a header-unaware offset:
  whatever mechanism is used either accounts for the measured header or does not
  scroll at all." The *does not scroll at all* half is pinned by Jest; the
  *accounts for the measured header* half is not.

No number is invented for anything unmeasured: the landing offset, the time to
land, and the swipe count are all **UNMEASURED**.

### Owner's iPhone check (product-owner run)

Build: `npx expo start --clear`, physical iPhone, Expo Go. No JDK / simulator /
Android SDK here, so a build stage cannot drive this.

1. **Set up.** Create (or open) a pattern of 24 steps. Mark steps 1-19 complete
   so **step 20 is the current step**. Go back to the library.
2. **AC1 — opens at the step.** Reopen the pattern. **Expect:** the row reading
   *Row 20 / Current step* is at the **top of the step area**, fully visible,
   with **no manual swipe**. Threshold: it is there by the time the steps have
   finished appearing — no swipe, and no waiting past about a second.
3. **AC2 — the landing point is header-aware.** **Expect:** the top of the step
   area is the step row. If the counter card, the *Edit pattern* row, or the
   title is what sits there instead, the offset is header-unaware and the
   mechanism is wrong — file that, do not adjust it away.
4. **One snap, not a glide.** **Expect:** the jump is instantaneous
   (`animated: false`) and happens **once** — no visible glide, and no second
   jump after it settles (which would mean the capped retry is still firing
   after a successful landing).
5. **The header is above, not consumed.** Swipe up. **Expect:** the title,
   progress summary and counter are all still there.
6. **The yank guard.** From the restored position, swipe down to step 22, then
   tap *Mark step 20 complete*, then tap *+* on the counter. **Expect:** the list
   does **not** move on either tap. (Jest pins the call count; only the device
   pins that nothing moves.)
7. **A fresh pattern does not jump.** Open a pattern whose current step is step 1.
   **Expect:** it opens at the top with no jump at all.
8. **Android.** All seven, on an Android device — no Android SDK or `adb` here,
   so nothing in this issue ran on Android.

### The edited flow leg has never been executed

Like every `.maestro` flow in this repository (`smoke-verification.md` §4). The
post-restart leg now scrolls **UP** to `2 of 3 steps done` before asserting it,
because on the 3-step fixture steps 1-2 complete makes step 3 current and the
viewer opens with the progress summary scrolled off. Both selectors are
standalone metacharacter-free `Text` nodes — `2 of 3 steps done` is a
`CraftAnnouncement`, `Current step` is the status pill; `PatternViewerStepRow`'s
outer element is a plain `View` and only the checkbox is an `accessible`
`CraftPressable`, so neither string is buried inside a merged row label. Both
assertions are positive, so neither can pass vacuously. The leg passes whether or
not the restore fires, so the flow is deliberately not itself a bet on this
feature — which also means it is **not** evidence for AC1. First real run is #16.

### Out of scope, on the record

- **The guide working view keeps no such jump** (owner decision 3). This is not
  an accidental gap: `src/features/guides/presentation/useGuideViewer.ts` passes
  `activeStepId: undefined` at **both** call sites, so a guide's "current step" is
  always just the first incomplete one — there is no persisted pointer to restore
  and no `FR-GU` equivalent to FR-PV-05. A follow-up may be filed after this
  mechanism proves out on device; this PR opens none.
- **A stale test title survives on purpose.**
  `tests/PatternViewerScreen.test.tsx`'s `'still restores the current step far
  down a long pattern, without the mount-time jump'` is still true in every
  assertion — it only ever pinned the durable position — but its *name* now
  describes a world this issue ends. #63 AC4 freezes that block unchanged, and a
  title-only edit is still an edit, so it is left byte-identical for the retro to
  rename in its own PR (plan D5).
- **One residual header-unaware path exists and is unreachable here.** In
  `ListMetricsAggregator.getCellMetricsApprox`, an index at or below
  `highestMeasuredCellIndex` whose own cell was never measured falls back to an
  average-length estimate, which is header-unaware. Cells are laid out
  contiguously from 0 during the initial fill, so this cannot occur inside the
  startup window the five-attempt cap confines the restore to. Recorded so a
  future change that moves the trigger out of that window knows what it reopens.
