### Five specific residual risks for the #16 device pass

1. **The real OS paste gesture is never exercised — and it is the whole gesture
   this issue ships.** Maestro's `inputText` types characters into the field; it
   does not open the iOS/Android paste menu. Whether a maker can actually
   long-press a YouTube video description in the YouTube app, copy it, and paste
   it into `guide-paste-field` — including whether the app's own paste menu
   appears on a `multiline` `TextInput` under iOS 26 — is provable only on a real
   device with the real YouTube app. Deliberately, no `expo-clipboard`
   programmatic read exists to fall back on (architecture §9.2: it would raise
   the iOS 16 "Allow Paste" prompt for nothing).
2. **`inputText` with embedded newlines into a `multiline` `TextInput` is
   unverified.** Legs 1 and 2 send a four-line block in one `inputText`. If the
   platform's IME submits on the newline instead of inserting it, the flow fails
   at the field — a *harness* failure that looks identical to a parser failure.
   Before filing a parse bug, confirm the field actually holds four lines; if it
   does not, split the `inputText` per line or use a YAML block scalar.
3. **Leg 4's library-row tap inherits `guide-authoring.yaml`'s title
   assumption.** `tapOn: "Amigurumi Basics"` matches `guideRowAccessibilityLabel`
   only while the guide has no creator — i.e. only while the offline metadata
   lookup genuinely failed. On iOS, where airplane mode is a manual Control-Centre
   step rather than `setAirplaneMode`, a lookup that succeeded makes the row read
   `Amigurumi Basics. By <creator>`, and the tap misses. Put the device in
   airplane mode before running the flow on iOS, and read a miss here as a
   preamble problem, not a persistence bug.
4. **Leg 2 asserts and taps without scrolling, and the flow was written blind.**
   Leg 2 asserts `Step 4 of 4 at 5:03: Fasten off` and then taps `Back to guide`;
   leg 1 asserts the editor's empty-state string after the paste section. Maestro's
   `assertVisible` and `tapOn` **do not scroll** — they act on what is already in
   the viewport. On a phone the paste field sits between the step rows and the
   hand-typed *Add a step* field, so after four steps land, the fourth row, the
   header button, and the paste section are unlikely to share one screen. Read a
   miss at any of those selectors as a **scroll/viewport problem first**, not a
   product bug: add a `scrollUntilVisible` (or `scroll` then re-assert) ahead of
   the selector and re-run before filing anything. Same guidance as risk 2 — a
   blind flow's first failure is nearly always the harness.
5. **Paste a real web transcript-panel copy, not only the Maestro fixture.**
   Some browsers copy the transcript panel with a **blank line between every
   cue**. By the parser's own blank-line rule each cue then becomes its own
   block, so a long transcript in that shape yields one step per cue and is
   refused as `too-many-steps` rather than merged into 30 s blocks. That is
   spec-conformant — the blank-line break is a deliberate, tested rule (`breaks a
   cue run at a blank line rather than swallowing it`) — but it means the cue
   path's *realistic* clipboard shape has never been seen end to end. During the
   device pass, copy an actual transcript panel from the web and paste it: if it
   arrives double-spaced and is refused, that is a product question for the
   owner (should a blank line between *every* line be treated as formatting
   rather than as a run break?), not a Maestro failure. Record the answer here.
